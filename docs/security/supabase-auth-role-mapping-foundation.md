# Supabase Auth Role Mapping Foundation

## Purpose
Define how Supabase Auth identities (`auth.uid()`) are mapped to WMS application roles via the `tgd_user_profiles` table. This provides a deterministic, backend‑enforced source of truth for role‑based access control (RBAC) and customer isolation.

## Supabase Auth Identity Model
- Supabase authentication yields a unique immutable identifier `auth.uid()` for each user.
- The identifier is never exposed to the frontend as a decision‑making token; it is only used to look‑up the user profile.

## `tgd_user_profiles` Mapping Model
```sql
CREATE TABLE tgd_user_profiles (
  id uuid PRIMARY KEY,
  auth_user_id uuid NOT NULL,            -- matches auth.uid()
  email TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin','warehouse_manager','warehouse_staff','accounting','viewer')),
  customer_id uuid NULL,                -- optional, for customer‑scoped staff
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```
- The `role` field is the single source of truth for backend RBAC.
- `customer_id` links staff to a specific customer when needed.
- `is_active` allows quick de‑provisioning without deleting the record.

## Role Resolution Flow
1. Frontend receives an authenticated user object from Supabase (`authUser.id`, `authUser.email`).
2. Backend (or a safe wrapper service) queries `tgd_user_profiles` by `auth_user_id`.
3. The profile is passed to **resolveUserProfileRole** which determines the effective WMS role, handling inactive, missing, or unknown roles.
4. The resolved role is cached for the request lifecycle and used by RLS policies and backend permission checks.

## Role Definitions
| Role | Description |
|------|-------------|
| **admin** | Full system access, can manage users, configure RLS, and run admin‑only RPCs. Must be explicitly set and active. |
| **warehouse_manager** | Oversees warehouse operations; can read/write receiving, putaway, transfer, adjustment, stock‑count, withdrawal, allocation, picking, and dispatch tables. |
| **warehouse_staff** | Performs day‑to‑day warehouse tasks; read/write most operational tables except admin‑level configuration. |
| **accounting** | Reads accounting charge staging, monthly storage billing, and audit logs; no write access to operational tables. |
| **viewer** | Read‑only view of all tables; used as a safe fallback for missing/unknown profiles. |

## Customer Scope Model
- `customer_id` on the profile (when present) limits access to rows where `customer_id` matches the profile’s value. This is enforced by RLS policies (see Sprint 13C).
- Roles without a `customer_id` (admin, accounting, viewer) have global visibility per their permissions.

## Missing Profile Behavior
- If no profile is found for a given `auth.uid()`, the system resolves the role to **viewer** and marks the reason `missing_profile`. This ensures the user cannot modify data.

## Unknown Role Behavior
- If the `role` field contains a value not in the known list, resolution falls back to **viewer** with reason `unknown_role`.

## Admin Safety Rule
- The **admin** role is granted **only** when the profile’s `role` is exactly `admin` **and** `is_active` is true. No default admin is assumed.

## Viewer Fallback Rule
- All other conditions (null, empty, unknown, inactive, missing profile) resolve to **viewer**.

## Frontend Responsibility
- The frontend may display menus/routes based on the resolved role but must never enforce security decisions. All critical checks are performed server‑side via RLS and backend services.

## Backend / RLS Responsibility
- Backend services call `supabaseAuthRoleMappingService` to obtain the resolved role.
- RLS policies reference `auth.uid()` and the role derived from `tgd_user_profiles` to enforce row‑level permissions.
