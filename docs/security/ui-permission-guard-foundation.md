# UI Permission Guard Foundation

## Overview

This document describes the **frontend‑only permission guard** introduced in Sprint 8B. It provides utilities and a React component that allow UI elements to be conditionally displayed based on the current user's role.

## Components & Utilities

| File | Export | Purpose |
|------|--------|---------|
| `src/security/permissionGuard.js` | `ROLE_HIERARCHY`, `hasRoleAccess`, `canAccessRoute`, `getRouteAccessDecision`, `createPermissionGuardContext` | Pure functions that compute access decisions using the route permission catalog.
| `src/security/PermissionBoundary.jsx` | `PermissionBoundary` (default) | React component that renders `children` when access is allowed, otherwise renders an optional `fallback` element. No redirects or side‑effects.

## Usage Example
```jsx
import PermissionBoundary from 'src/security/PermissionBoundary.jsx';
import { useAuth } from 'src/auth/useAuth'; // hypothetical auth hook returning { role }

function AccountingReport() {
  const { role } = useAuth();
  return (
    <PermissionBoundary userRole={role} routePath="/reports/accounting-charge-handoff-review">
      <AccountingChargeHandoffReviewPage />
    </PermissionBoundary>
  );
}
```

## Design Decisions
- **Frontend‑only**: No backend RLS or database changes. All checks happen in the browser using the existing `routePermissionCatalog`.
- **Pure functions**: No network calls, storage, or side‑effects.
- **Extensible**: New routes can be added to `routePermissionCatalog.js` and the guard will automatically respect them.

## Safety Checks
- No redirects, logout calls, or Supabase interactions.
- Does not modify business workflow or data persistence.
- Does not enforce backend security. It is a UI convenience layer only.
